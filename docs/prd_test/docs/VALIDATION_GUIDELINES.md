# VALIDATION_GUIDELINES — 오목 로직 교차 검증 가이드라인

> 강의의 "퀴즈 문제 교차 검증 가이드라인(정답이 하나뿐인가 / 최상급 기준 / 시간·범위 / 교차 검증)"을
> **오목 규칙 엔진 · AI · 복기 분석 · LLM 해설**에 맞게 바꾼 것이다.
> 기능을 만들거나 고칠 때마다 아래 4가지 + 추가 3가지를 확인한다. `/omok-validate` 명령이 이 문서를 기준으로 점검한다.

---

## 모든 기능 작성 시 확인 사항

### 1. 정답이 하나뿐인가? (규칙 해석의 유일성)

- 승패·금수·무승부 판정은 **한 가지 해석**만 가능해야 한다. 다른 해석이 가능하면 조건을 명시한다.
  - 예: "6목은 승리인가?" → **자유룰: 승리 / 렌주룰 흑: 승리 아님(금수)**. 판정 함수는 항상 `ruleset`을 인자로 받는다.
- 기준 문서는 `docs/GAME_RULES.md`다. 코드·테스트·해설이 이 문서와 다르면 **코드가 틀린 것**으로 본다.
- 확인:
  - [ ] 모든 판정 함수가 `ruleset`을 명시적으로 받는가(전역 상태 의존 금지)
  - [ ] 5목 이상/정확히 5목, 6목, 마지막 수와 판 가득 참 동시 발생 등 모호한 경우가 `GAME_RULES.md §9`에 명시되어 있는가
  - [ ] 같은 입력에 대해 판정 결과가 항상 같은가(무작위·시간 의존 없음)

### 2. 최상급·평가 표현에 기준이 있는가? (평가의 객관성)

- "최선의 수", "패착", "결정적 수", "승률", "난이도 상" 같은 표현은 **측정 기준**이 코드와 문서에 있어야 한다.
  - "패착" = 둔 사람 관점 `loss > 0.20` 또는 하드 규칙(놓친 승리·필수 방어 실패) — `config.CLASS_THRESHOLDS`
  - "최선" = **엔진 v{engine.version}, 깊이 {depth}, 평가 {wpScale} 기준** 1순위 — 절대적 최선이 아니다
  - "결정적 수" = 승률 변화 상위 K개 + 승패 직결 수 — 선정 규칙은 `PRD_STEP_02 §1.3`
- UI·해설에서 "무조건 최선", "완벽한 수" 같은 **단정 표현 금지**. "엔진 기준 최선"처럼 기준을 드러낸다.
- 확인:
  - [ ] 임계값·가중치·점수표가 `constants/config.js` **한 곳**에만 있는가(매직 넘버 금지)
  - [ ] 난이도 정의(하/중/상)가 파라미터 표와 일치하고 `selfplay` 결과로 순서가 증명되는가
  - [ ] 복기 결과에 `engine.version/depth/wpScale`이 기록되는가

### 3. 시간과 범위가 명확한가? (좌표·버전·모델)

- **좌표계:** 내부 `(x,y)` 0-index 좌상단 원점, 표시 라벨 `A1`~`O15`(행은 위→아래), 수 번호 1-index. 변환은 `toLabel/fromLabel` **한 곳**.
- **버전/시점:** 기보·복기 데이터에는 `version`, 엔진 버전, 사용한 모델 ID, 생성 시각을 남긴다. 모델·무료 요금제는 바뀔 수 있으므로 **모델 ID는 `.env`**로만 지정한다.
- **범위:** 판 크기(15), 수 번호 범위(1~225), 좌표 범위(0~14)를 입력 경계에서 검증한다.
- 확인:
  - [ ] 좌표를 문자열로 직접 조립/파싱하는 코드가 `board.js` 밖에 없는가
  - [ ] 네 모서리·가장자리 케이스가 테스트에 있는가
  - [ ] 저장 데이터에 `version`이 있고 읽을 때 검사하는가

### 4. 교차 검증했는가? (서로 다른 방법으로 확인)

- 의심스러운 결과는 **서로 다른 방법 2가지 이상**으로 확인한다.
  - 승리 판정: ① 4방향 스캔 구현 ② 테스트의 **전체 판 브루트포스 판정기**(느려도 단순한 구현)로 무작위 국면 1,000개 비교
  - AI 난이도: ① 단위 테스트(필수 방어·즉시 승리) ② `selfplay` 승률
  - 복기 분류: ① 고정 국면 기대값 테스트 ② 같은 기보 2회 분석 시 결과 동일
  - LLM 해설: ① 서버 검증기(좌표·사실 대조) ② 스모크 테스트 반복 호출
- 논란 있는 규칙(렌주 금수의 엣지 케이스)은 **공식 렌주 규정**을 기준으로 하고, 선택한 해석을 테스트 이름에 남긴다.
- 확인:
  - [ ] 브루트포스 판정기와 실제 판정기가 불일치한 사례가 0건인가
  - [ ] 버그를 고칠 때 **재현 테스트를 먼저** 추가했는가

## 추가 확인 사항 (AI API 프로젝트용)

### 5. LLM 출력은 믿지 않고 검증하는가? (할루시네이션·오류·제멋대로)

- LLM은 **수의 판정을 하지 않는다.** 엔진이 정한 사실을 설명만 한다.
- 서버는 LLM 응답을 항상 검증한다: JSON 파싱 → 스키마 → 대상 수 일치 → **허용 좌표 목록 대조** → 사실 모순(분류와 반대되는 평가) 검사.
- 검증 실패 시 **해당 항목만 템플릿으로 대체**하고, 출처 배지로 사용자에게 알린다.
- 사용자 입력 문자열(닉네임 등)은 LLM에 **보내지 않는다**(프롬프트 인젝션 방지).
- 확인:
  - [ ] 환각 좌표(`Z99`, `P3`, 허용 밖 좌표)가 담긴 가짜 응답이 폐기되는가
  - [ ] 깨진 JSON/빈 응답/타임아웃/429/키 없음에서 복기가 끝까지 동작하는가
  - [ ] 스모크 테스트(T-1~T-7) 결과와 채택 모델이 `docs/API_TEST_REPORT.md`에 있는가

### 6. 비밀·비용·제한을 지키는가?

- [ ] `.env`가 `.gitignore`에 있고, 키가 클라이언트 번들·로그·에러 응답에 없다(빌드 산출물 grep)
- [ ] 한 판당 LLM 호출 수가 정상 1회/최대 3회 이내, 같은 기보는 캐시 사용
- [ ] 요청 크기·분당 호출 수 제한이 있다
- [ ] 무료 모델의 요청 제한(429)을 장애가 아닌 정상 경로로 처리한다

### 7. 사용자 경험의 일관성을 지키는가?

- [ ] 분류 색·기호·라벨이 `constants/colors.js` 한 곳에서만 정의되고 모든 화면이 참조한다
- [ ] 색만으로 의미를 전달하지 않는다(기호+텍스트 병기)
- [ ] 대국→복기→새 대국 전환 시 이전 상태가 남지 않는다(기보 배열·턴·선택 수·필터·타이머 리셋)
- [ ] 로딩/빈/오류 상태가 모두 존재한다
