# PROMPTS — 단계별 실습 프롬프트 (오목 복기 마스터 버전)

> 강의 실습의 프롬프트(퀴즈 게임 · 냉장고 앱)를 **오목 + AI 복기** 주제에 맞게 바꾼 것이다.
> 코드 블록 안의 문장을 그대로 붙여넣으면 된다. `[ ]`로 표시된 곳만 상황에 맞게 바꾼다.
> (Notion MCP 등 MCP 연동 단계는 이번 범위에서 제외)

## 0. 진행 순서와 현재 준비 상태

| 강의 실습 | 오목 버전 | 이 패키지에서의 상태 |
|---|---|---|
| T1 · PRD 작성 (Claude Desktop 채팅) | 오목 서비스 3단계 PRD | ✅ 완성본 포함 (`PRD_STEP_01~03.md`). 다시 만들고 싶을 때만 §T1 사용 |
| T2 · PRD 파일 저장, `/init`, `/memory`, CLAUDE.md, 가이드라인 점검 | 오목 로직 교차 검증 가이드라인 | ✅ `CLAUDE.md`에 가이드라인 포함. §T2로 확인·점검 |
| T3 · `.claude/commands` 커스텀 명령어 | `/omok-validate`, `/run-step` | ✅ 파일 포함. §T3로 만들기 연습·실행 |
| T4 · AI API 바이브코딩 (OpenRouter) | 수별 복기 + AI 해설 | ⏳ 구현은 §T4 프롬프트로 진행 |

**처음 시작하는 순서**
1. 새 프로젝트 폴더를 만들고 이 패키지의 파일을 그대로 복사한다(`.claude` 폴더 포함).
2. 터미널에서 그 폴더를 열고 `claude` 실행 → §T2 → §T3 → §T4 순서로 진행.

## T1. PRD 작성 (Claude Desktop — 채팅)

강의의 "상식 퀴즈 PRD 작성" 프롬프트를 오목으로 바꾼 것. 5W1H로 먼저 기획한 뒤 3단계 PRD를 요청한다.

```
오목 게임 웹 서비스를 기획하고 싶어. 먼저 5W1H(Why/Who/What/When/Where/How)로 서비스 기획을 정리하고,
그 기획에 합당하게끔 실제 제품처럼 개발하기 위한 3단계의 상세 PRD를 작성해줘.

[메인 기능]
- 15×15 오목, 기본은 자유룰(5목 이상 승리), 렌주룰(금수)은 옵션
- AI와 두기: 난이도 하/중/상 선택. 2인 로컬 대전도 가능
- 승패를 즉시 판정하고 결과 화면 표시

[서브 기능]
- 대국이 끝나면 전체 기보를 AI API(OpenRouter 텍스트 모델)에 넘겨 수별로 평가
- 평가 결과를 5단계 색상(최선/좋음/보통/실착/패착)으로 표시해서 한눈에 복기
- 승부를 가른 결정적 수만 강조해서 골라 볼 수 있게, 더 좋은 수(최선 수)도 제시
- 기보 저장, 프로필, 전적

[제약]
- 대국 AI는 로컬 엔진, LLM은 복기 해설에만 사용 (LLM이 좌표를 지어내는 환각 대비책 포함)
- 디자인은 미니멀한 모던 UI(애플 감성), React 기반
- 단계 구성: 1단계 코어 대국 / 2단계 AI API 복기 / 3단계 시각화·저장
- 각 단계에 목표, 구현 내용, 수락 기준, 테스트 시나리오를 포함
```

## T2. 프로젝트 파일 세팅 · `/init` · `/memory` · CLAUDE.md · 가이드라인 점검

### T2-1. PRD 파일 저장 (채팅에서 PRD를 새로 만든 경우에만)

```
지금 작성한 PRD를 각각 docs/PRD_STEP_01.md, docs/PRD_STEP_02.md, docs/PRD_STEP_03.md 파일로 현재 프로젝트 폴더에 생성해줘(저장해줘).
```

### T2-2. `/init`

터미널(Claude Code)에서:

```
/init
```

이미 `CLAUDE.md`가 있는 상태라면 덮어쓰지 않도록 이렇게 요청해도 된다.

```
/init 실행 시 기존 CLAUDE.md의 "핵심 설계 결정", "오목 규칙 요약", "로직 교차 검증 가이드라인" 섹션은 삭제하거나 바꾸지 말고, 아직 비어 있는 부분(실제 명령어·폴더 구조)만 현재 프로젝트 상태에 맞게 보완해줘.
```

### T2-3. `/memory` 로 가이드라인 확인·추가

```
/memory
```
→ **Project memory** 선택 → 시스템 에디터에서 `CLAUDE.md`가 열림 → 가이드라인 추가/수정 후 저장.
(이 패키지의 `CLAUDE.md`에는 아래 "로직 교차 검증 가이드라인"이 이미 들어 있다.)

붙여넣을 가이드라인 원문(강의 "퀴즈 문제 교차 검증 가이드라인"의 오목 버전):

```
## 로직 교차 검증 가이드라인 (모든 기능 작성 시 확인)
1. 정답이 하나뿐인가?
   - 규칙 해석이 갈릴 수 있으면 조건 명시 (예: 6목 → 자유룰 승리 / 렌주룰 흑 금수)
2. 최상급·평가 표현에 기준이 있는가?
   - "최선", "패착", "결정적 수", "난이도 상" 등에 측정 기준(엔진 버전·깊이·임계값) 명시
3. 시간과 범위가 명확한가?
   - 좌표계(0-index, 좌상단), 수 번호(1-index), 판 크기(15) 명시
   - 변할 수 있는 정보(모델 ID, 엔진 버전)는 시점·버전 기록
4. 교차 검증했는가?
   - 의심스러운 결과는 서로 다른 방법 2가지 이상으로 확인
   - 논란 있는 규칙(렌주 금수)은 공식 렌주 규정 기준
5. LLM 출력은 믿지 않고 검증한다 (좌표 환각·사실 모순 검사, 실패 시 템플릿 폴백)
```

### T2-4. CLAUDE.md 확인

```
현재 프로젝트의 CLAUDE.md 내용을 확인해줘.
```

### T2-5. 가이드라인으로 점검 (코드가 생긴 뒤에 사용)

강의의 "지금까지 만들어진 문제를 가이드라인으로 점검" 프롬프트의 오목 버전:

```
지금까지 만들어진 오목 규칙 엔진·AI·복기 분석 코드와 테스트를 방금 저장한 로직 교차 검증 가이드라인을 참고해서 점검해 줘.
가이드라인에 맞지 않는 로직, 테스트, 문서가 있다면 재현 테스트를 먼저 추가한 뒤 이에 맞게 수정해줘.
```

코드가 아직 없을 때(PRD 단계)에는:

```
docs/PRD_STEP_01.md ~ PRD_STEP_03.md와 docs/GAME_RULES.md를 로직 교차 검증 가이드라인에 비춰 점검해 줘.
규칙 해석이 모호하거나, 평가 기준이 불명확하거나, 서로 모순되는 부분이 있으면 목록으로 알려주고 수정안을 제안해줘. (수정은 내가 승인한 뒤에)
```

## T4. AI API 바이브코딩 — OpenRouter로 수별 복기 + AI 해설

> 강의 모델 메모: 텍스트 `google/gemma-4-26b-a4b-it:free`. 강의에서 이미지 모델로 적었던 `google/veo-3.1`은 **영상 생성 모델**이고,
> 이 서비스는 이미지 입력이 필요 없으므로 **텍스트 모델만** 사용한다. 무료 모델은 요청 제한·변경이 있을 수 있어 아래 테스트로 확정한다.

### T4-1. API 키 준비 (직접 하는 부분 + 프롬프트)

직접: [openrouter.ai](https://openrouter.ai) 가입 → API 키 발급 → 프로젝트 폴더의 `.env` 파일에 저장

```
OPENROUTER_API_KEY=여기에_키_붙여넣기
OPENROUTER_MODEL=google/gemma-4-26b-a4b-it:free
```

프롬프트:

```
OpenRouter에서 받은 API 키를 .env 파일로 저장했어. 이 키를 안전하게 사용할 수 있도록 준비해 줘.
.gitignore에 .env가 들어 있는지 확인하고, .env.example을 만들고(키 이름만, 값 없이),
키는 서버 코드에서만 읽고 브라우저 코드·로그·에러 응답에 절대 나오지 않게 해줘. 키 값은 어떤 출력에도 보여주지 마.
```

### T4-2. API 테스트 (꼭 필요 — 할루시네이션 · 오류 · 제멋대로)

강의의 "API가 실제로 작동하는지 테스트" 프롬프트를 복기 해설 용도에 맞게 바꾼 것:

```
이제 준비된 API가 실제로 작동하는지 테스트해 줘.
텍스트 인식(생성)은 google/gemma-4-26b-a4b-it:free 모델을 이용할 거야. (이미지 모델은 사용하지 않아)
오목 복기 해설 용도로 아래를 각각 테스트해서 실행 결과를 표로 알려줘.
1) 연결·인증이 되는가
2) 한국어로 짧게 답하는가
3) "JSON만 출력해"라고 했을 때 JSON.parse가 되는 JSON을 주는가 (10회 중 몇 회 성공?)
4) 5수짜리 샘플 국면과 '사용 가능한 좌표 목록'을 주고 해설을 시켰을 때, 목록에 없는 좌표를 지어내지 않는가 (5회 반복)
5) 내가 "이 수는 패착이야"라고 사실을 줬을 때 "훌륭한 수"처럼 사실과 반대로 말하지 않는가 (5회 반복)
6) 잘못된 키, 빈 키, 아주 짧은 타임아웃, 존재하지 않는 모델일 때 서버가 죽지 않고 오류를 정리해서 돌려주는가
7) 응답 시간(중앙값)
테스트 스크립트는 scripts/api-smoke-test.js 로 만들고, 결과는 docs/API_TEST_REPORT.md 에 저장해줘.
안 되거나 기준 미달이면, 사용 가능한 다른 무료 텍스트 모델 후보를 3개 이상 알려주고 가장 적절한 것으로 같은 테스트를 해서 비교한 뒤 채택 이유와 함께 .env의 OPENROUTER_MODEL을 정해줘.
```

### T4-3. 단계별 실행 (강의: "PRD_step1.md를 실행해. 메인 애플리케이션을 실행해서 1단계의 결과를 테스트해 줘.")

공통 머리말(처음 한 번):

```
React(Vite) 기반으로 만들어 줘. 상세 규칙은 CLAUDE.md와 docs/GAME_RULES.md를 따르고, 각 단계의 PRD에 있는 수락 기준을 모두 통과시켜줘.
```

**1단계**

```
docs/PRD_STEP_01.md를 실행해.
메인 애플리케이션을 실행해서 1단계의 결과를 테스트해 줘.
```

**2단계** (API 테스트 T4-2가 끝난 뒤)

```
docs/PRD_STEP_02.md를 실행해.
메인 애플리케이션을 실행해서 2단계의 결과를 테스트해 줘.
```

**3단계**

```
docs/PRD_STEP_03.md를 실행해.
메인 애플리케이션을 실행해서 3단계의 결과를 테스트해 줘.
```

같은 일을 커스텀 명령어로: `/run-step 1` · `/run-step 2` · `/run-step 3`

### T4-4. 단계별 점검 프롬프트

```
방금 1단계 결과를 PRD의 수락 기준(AC) 표 기준으로 항목별 통과/실패로 정리해줘. 실패한 것은 원인과 수정 계획을 알려주고, 내가 승인하면 고쳐줘.
```

```
/omok-validate engine
/omok-validate ai
/omok-validate analysis
/omok-validate api
```

### T4-5. 마무리 점검·시연 준비

```
최종 점검을 해줘. (1) 빌드 산출물과 로그에서 API 키 문자열이 없는지 검색해서 확인 (2) .env를 지우고 서버를 재시작했을 때도 복기가 템플릿 해설로 동작하는지 확인 (3) 대국→복기→새 대국을 5번 반복해서 이전 상태가 남지 않는지 확인 (4) README.md의 시연 스크립트(약 3분)를 처음부터 끝까지 따라 해보고 막히는 곳을 알려줘.
```

## 참고. Gemini CLI로 구현할 때

- `CLAUDE.md`를 `GEMINI.md`로 복사(또는 이름 변경)해서 프로젝트 루트에 둔다. 내용은 그대로 사용 가능.
- `.claude/commands/*.md`는 Gemini CLI의 커스텀 명령어 형식과 다르다. 명령어 대신 `omok-validate.md`, `run-step.md`의 본문을 프롬프트로 직접 붙여넣어 사용한다.
- PRD 실행 프롬프트(§T4-3)는 동일하게 사용한다.
